# DeepSeek 峰谷状态查询页

> 一个纯静态网页，只回答一个问题：DeepSeek 现在是否处于高峰计费时段？

**Languages:** [English](README.md) | 简体中文

## 概述

页面给出当前状态、距下次切换的倒计时、今天的 24 小时时间轴、未来 14 天的热力日历，以及一份用大白话写的切换预告。页面以静态文件发布：无需构建、打包、安装依赖或服务端运行时。`package.json` 提供可选的 Node 维护命令；页面运行时不会加载这些工具。

判断逻辑是从本机一个 macOS 菜单栏 app **逐行移植**过来的，写法上力求与之一致。这个一致性就是整个项目的意义所在：一旦网页与 app 出现分歧，它就不只是没用，而是有害 —— 一个自信但错误的「空闲」，正是会让人按两倍价格去付费的东西。

## 与 DeepSeek 无任何关联

**高峰时段规则本身就是 DeepSeek 的，转录自其定价页；节假日安排则不是。**

| 数据源 | 是什么 | 谁在运营 |
| --- | --- | --- |
| `api-docs.deepseek.com/quick_start/pricing` | 高峰时段规则，手工转录 | DeepSeek |
| `holiday-cn`（经 jsDelivr） | 国务院节假日安排的转载 | 社区项目 |

本页与 DeepSeek **没有任何隶属、背书或关联关系**。它只是对一条公开规则的独立实现。

节假日数据源目前返回宽松的 CORS 头。那是善意，不是承诺：它随时可以改，而这正是要有每日快照兜底的原因。长期可用性不在本项目控制之内。

## 工作原理

只有两层，没有第三层：

1. **规则提供小时。** 两个窗口以 iCalendar 文档的形式编译进页面，其 `RRULE` 被展开成一个个具体的窗口。
2. **北京日历删掉整天。** 周末与法定节假日全天按空闲计费，被调休指定为上班日的周末也照此办理。

第二层只能**删除**窗口，永远不能凭空造出一个。所以本地规则不可能制造出规则本身没有发布的高峰。

**页面宁可未知。** 规则是编译进页面的常量，不存在「取不到」的可能 —— 但规则读不出来时，答案依然是 `UNKNOWN`，绝不会猜成「空闲」。节假日数据是下载来的，它的失败方式是降级而非失败：取不到就退化为「仅周末规则」，诊断抽屉里会写明。

> ⚠️ 一个自信的绿色「空闲」，是本页唯一可能让人真金白银多花钱的输出。下面每一条设计决策都源自这一句话。

### 降级策略

解析器的告警是分级的，因为它们指向的方向并不相同：

- **`window-drop`** —— 任何可能删除或缩短窗口的问题：无法解析的 `TZID`、无法解析的 `DTSTART` 或 `RRULE`、超出范围的 `INTERVAL`/`COUNT`、缺失的 `DTEND`。它们都会把结果*推向*空闲，而这正是一个「宁可未知」的产品最不能漂移的方向。出现其中任何一条，空闲大卡就会从绿色降级为琥珀色，并钉上一个角标。
- **`ignored-part`** —— 不支持的规则分支（例如 `BYSETPOS`）以及未知属性。它们改变不了状态，因此只在诊断抽屉里列出，别的什么都不做。

降级解析永远不会导致凭空造出高峰。如果所有事件都被丢弃，时间轴就是空的，答案就是 `UNKNOWN`。

### 更新规则

规则是手工转录的，它的新鲜度就等于「上一个人读官方页」的那一天。DeepSeek 的经营政策随时可能变；变的时候：

1. 改 `web/src/sources.js` 里的 `OfficialRule.calendar` —— 两个窗口写成 UTC 的 `DTSTART`/`DTEND` 对。那两行里的**日期是固定锚点、没有含义**，只有时刻有意义。
2. 把 `OfficialRule.transcribedOn` 改成你核对的那一天。源信息条与诊断抽屉都会显示它，这正是让「转录过期」可见而不是静默的原因。
3. 跑 `npm run check-rule`。它会重新解析常量，并把每个窗口同时按 UTC 与北京时间打印出来，方便与官方页逐条对照。

第 3 步就是全部的自动化检查，而它**刻意不知道正确答案是什么**：把小时数写死进测试，等于每次政策变动都要改两个地方，而且一个「自洽但错误」的改动照样能通过。

**如果变动涉及「哪几天算高峰」，先停手。** 星期那一半不在那个文件里，它在 `web/src/models/off-peak-calendar.js`；「应用中国空闲规则」这个开关正是由这个分工定义的。一旦日历开始带 `BYDAY`，`check-rule` 就会失败，所以不可能不小心漏掉。

没有任何自动化把转录与官方页做比对。GitHub Actions 每季度会创建一条提醒人工复核的 issue，但不会自动检测官方规则是否变化 —— 见[已知盲区](#已知盲区)。

## 功能

### 四块板块

- **状态大卡** —— 用一个词给出当前状态（`PEAK HOURS`、`OFF-PEAK` 或 `UNKNOWN`）、距下次切换的每秒倒计时，以及同时以北京时间和访客本地时区显示的时刻。
- **24 小时时间轴** —— 今天画成一根条，标出高峰窗口、一条「现在」竖线，以及一张视觉隐藏但承载同样窗口信息的表格供屏幕阅读器使用。
- **14 天热力日历** —— 每列一个北京日、每行一小时：共 336 格，每一格都可聚焦且有标签。被整天抑制的日子会呈现为一整列连续的同色格子。
- **切换预告** —— 用大白话写出接下来的变化，例如「今天 14:00 进入高峰，持续 4 小时」。

### 语言与控件

- **中英双语。** 页面默认中文，切换无需刷新。节假日名称从不翻译，因此名称始终与它来源的那份官方公告一致。
- **中国空闲规则开关。** 关掉本地的周末与节假日规则，按规则原本的写法显示窗口，周末也包括在内。
- **诊断抽屉。** 列出每一条解析告警及其级别，并附上官方规则出处与上次核对该转录的日期。

### 图例必须写明的两个约定

「今天」在本页上刻意有两个不同含义：

- **时间轴**画在**访客**本地的日历日上，每个整点刻度都标注落在它上面的北京时间。
- **热力日历**画在**北京**日历日上，因为规则本来就是以北京日为单位的。

对北美的访客来说，这两天根本不重叠。没有图例的话，两张图会被读成互相矛盾。

### 每秒的 tick

时间轴在**每次数据加载时只展开一次**。之后每秒只是用二分查找去查询它，并且每次都重新读 `Date.now()`，而不是累加计数器 —— 否则一个被浏览器节流的后台标签页会越走越偏，而每秒重算 400 天的窗口会把 CPU 烧掉。

## 环境要求

- **看页面：** 近几年任何一个浏览器即可。页面用到 ES modules、`Intl.DateTimeFormat` 和 `fetch`，不带任何 polyfill，将来也不会带。
- **刷新随包的节假日数据，或检查规则：** Node 22 或更新版本。这是工具链的依赖，不是页面的。
- **部署：** 任何静态文件服务器。没有服务端运行时。

## 使用方式

### 本地运行

```sh
# 从仓库根目录起，这样才能验证相对路径在真实部署下成立
python3 -m http.server 8765
# 然后打开 http://127.0.0.1:8765/web/
```

页面必须通过 HTTP 访问，不能直接以 `file://` 打开 —— ES modules 和 `fetch` 都需要一个 origin。

### 部署

发布 `web/` 目录即可。它是自包含的：不需要构建、不需要安装、没有环境变量、没有服务端运行时、也没有配置文件。

- **任意静态主机** —— Netlify、Vercel、Cloudflare Pages、S3、nginx —— 把发布目录指向 `web/`。
- **GitHub Pages** —— 分支源只接受 `/` 或 `/docs`，所以 `web/` 要走 Actions 这条路线：`.github/workflows/pages.yml` 把 `web/` 作为 Pages artifact 上传。

网站通过 HTTPS 发布后，可在 iPhone/iPad 的 Safari 中打开，点分享按钮并选择「添加到主屏幕」。`web/manifest.webmanifest` 将启动方式设为独立窗口，并提供应用名称、颜色和图标；Service Worker 与离线缓存目前未启用，因此节假日数据仍按网页当前逻辑在线获取并在失败时使用随包快照。

页面运行时唯一会从自己 origin 取的东西，是它自己目录下的 `data/`，所以放在子路径下也能正常工作，不需要任何 base URL 配置。

## 仓库结构

JavaScript 实现从本机 macOS 应用逐文件移植而来。原始 Swift 源码不在本仓库中；这里展示的是网页实现。

```text
deepseek-peak-status/
├── README.md                    # English
├── README.zh-CN.md              # 简体中文
├── LICENSE                      # MIT
├── package.json                 # 无依赖；规则自检、快照与起服务脚本
├── web/                         # 可发布的站点 —— 发布这一个目录
│   ├── index.html               # 外壳；不跑 JS 也有中文文案
│   ├── styles.css               # 两套配色方案的 token，不加载任何网络字体
│   ├── assets/                  # 状态卡片使用的鲸鱼娘插画
│   ├── data/                    # 随包的节假日兜底数据，每日刷新
│   └── src/
│       ├── sources.js           # 编译进页面的高峰规则，以及节假日数据源
│       ├── support/             # 网页专用的辅助工具
│       ├── models/              # 从本机应用的模型移植
│       ├── services/            # 从本机应用的服务移植
│       └── ui/                  # i18n、四块板块，以及 app.js
└── tools/
    ├── check-rule.mjs           # 自检转录在 web/src/sources.js 里的规则
    └── snapshot.mjs             # 定时任务：刷新 web/data
```

`tools/` 下的东西，页面运行时够不着；它只放那个快照任务，而任务只往 `web/data/` 里写原始的节假日文档。

## 已知盲区

此处**如实声明，而非粉饰** —— 这些是引擎与页面本身的边界，不是某个测试套件的边界。

- **转录本身。** 规则是从一页散文里手工转录过来的。没有任何自动化去比对两者，所以那一页若有静默改动，本页会一直错到有人再去读一遍 —— 这也正是诊断抽屉要显示「上次核对该转录的日期」的原因。
- **编译进来的规则用不到的 RRULE 形态。** 展开器实现的是 RFC 5545 的一个子集 —— `FREQ`、`INTERVAL`、`COUNT`、`UNTIL`、`BYDAY`、`BYMONTHDAY`、`BYMONTH`、`WKST`。子集之外的写法一律拒绝而不是去猜；`P1M`/`P1Y` 这类 `DURATION` 写法尤其如此。
- **常见之外的时区。** 换算算术主要在 `Asia/Tokyo` 上检验，夏令时在 `America/New_York` 上检验；其它时区依赖 `Intl` 本身是对的。
- **夏令时切换与重叠。** `Foundation`/ICU 与 JavaScript 的 `Intl` 在春季缺口或秋季重叠处可能相差一小时。本移植钉死 `'compatible'` 约定（重叠取较早的那个瞬间，缺口向前跳过）。
- **400 天的展开视界。** 窗口只向前展开 400 天；超出之后，是 `covers()` 让页面不至于声称自己看到了更多。
- **渲染层。** 四块板块是手工构建、手工看过的。没有任何自动化检查它长什么样。
- **真实的 304 处理。** 浏览器传输层刻意不发 `If-None-Match`，因为它不在 CORS 安全列表内，会强制触发一个上游没有义务应答的预检请求。

## 常见问题

### 为什么显示 UNKNOWN？

因为编译进页面的高峰规则读不出来。这是本仓库的缺陷，不是网络状况：规则是常量，没有东西可抓、可缓存、可过期。`UNKNOWN` 不是一个需要想办法绕过去的错误状态，它就是诚实的答案，而且永远好过一个猜测出来的「空闲」。

### 时间轴和热力日历对「今天」的判断为什么不一样？

它们刻意画在不同的日历上 —— 时间轴按访客本地日，热力日历按北京日，因为规则本来就是以北京日为单位的。对北美的访客来说，这两天根本不重叠。页面上的图例已经写明了这一点。

### 为什么「空闲」大卡会变成琥珀色？

因为至少触发了一条 `window-drop` 告警，意味着规则里有一部分读不出来，可能有高峰窗口丢失了。只有确实不可能丢掉任何窗口时，这张卡才会保持绿色。

### 这是 DeepSeek 官方页面吗？

不是。见[与 DeepSeek 无任何关联](#与-deepseek-无任何关联)。节假日安排是第三方数据；高峰时段规则则是 DeepSeek 自己的，由本页手工转录。
